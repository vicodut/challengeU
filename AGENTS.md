# AGENTS.md

ChallengeU take-home: a coaching session booking app. The source of truth for *what* to build is the spec, GitHub issue #1, and its sub-issues #2–#26 (one ticket each, with native "blocked by" edges). The brief is the PDF at the repo root.

## Roles

- **Orchestrator** (Opus 5.5, the main session): picks tickets, dispatches implementers, runs reviews, opens PRs, talks to the human.
- **Implementer** (Sonnet 5.5 subagent): implements exactly one ticket inside its own git worktree.
- **Reviewer** (Opus 5.5): runs `/mattpocock-skills:code-review` on the implementer's branch.

## Ticket pipeline (orchestrator)

1. **Pick** a ticket whose blockers are all closed. Run one ticket at a time until #2 (scaffold) is merged. After that, run frontier tickets in parallel when their worktrees can use separate databases and ports.
2. **Dispatch**:
   - Create the ticket's worktree through Orca, never with raw `git worktree`:
     ```
     orca worktree create --repo name:challengeU --name <issue>-<slug> --branch feat/<issue>-<slug> --base-branch main --issue <issue> --json
     ```
   - Then dispatch a Sonnet 5.5 implementer **without** agent `isolation`, told to work only inside that worktree path.
   - The task prompt repeats the implementer rules below verbatim, because a worktree run may not load this file.
3. **Review** the branch with `/mattpocock-skills:code-review` on Opus 5.5. Resume the *same* implementer to fix every confirmed finding, then review the new commits again. After 2 rounds, list any remaining findings in the PR body and flag them to the human.
4. **Screenshot**: if the ticket touches `apps/web`, run the app and capture at least one screenshot of each screen the ticket touches with Claude in Chrome. Push the images to the orphan `pr-assets` branch and embed them in the PR body by URL.
5. **Open the PR** with `/mattpocock-skills:pr`:
   - title: a Conventional Commit, e.g. `feat(booking): student books a session`;
   - body: `Closes #<issue>`;
   - at least one Mermaid diagram: the request or event flow for API work, the route and component structure for web work;
   - a **Decisions** section listing the implementer's technical assumptions.
6. **Hand off**: stop and wait for the human. The human either approves (the orchestrator then merges with a merge commit) or merges it themselves. Never squash.
7. **Clean up** after the merge: remove the worktree with `orca worktree rm`, delete the local and remote branch, and confirm the ticket is closed.

The pipeline is done for a ticket when its PR is merged, its worktree and branch are gone, and its issue is closed.

## Implementer rules

- **Scope**: implement only your ticket's acceptance criteria. Every criterion is met and verified by a test or a command you ran.
- **Stop and report** to the orchestrator, without guessing, when:
  - you need a **new library** (see Libraries below);
  - you hit an **ambiguity** in a business rule or API contract that the spec and ticket don't settle.

  For small technical choices, pick a sensible default and record it under "Decisions".
- **Centralize utils**: before writing a helper, search for an existing one.
  - Helpers used by more than one module or feature go in that app's `shared/` folder.
  - A cross-app package is created only when both apps need the same pure function.
  - Domain rules stay inside their module.
  - Duplicated logic is a review finding.
- **Worktree only**: work, commit and push only inside your worktree and your branch.
- **Commits**: Conventional Commits, small and meaningful. The history is read by the evaluators.

## Ambiguity → grilling

When an implementer reports an ambiguity:
1. The orchestrator runs `/mattpocock-skills:grilling` with the human on Opus 5.5.
2. It posts the decisions as a comment on the ticket, starting with `> *This was generated by AI during triage.*`.
3. If a decision is domain-level, it updates the spec (#1), the ADRs and the glossary.
4. It resumes the implementer.

## Libraries

**Ask the human before adding any new direct dependency (runtime or dev) to any `package.json`.**

These are pre-approved, together with their direct companions (types, CLIs, peer plugins):
- backend: NestJS, `@nestjs/swagger`, `@nestjs/event-emitter`, class-validator/class-transformer, Drizzle ORM + drizzle-kit, `pg`, `@node-rs/argon2`;
- frontend: React, Vite, React Router, TanStack Query, Orval, shadcn/ui, Tailwind;
- tests: Vitest, `unplugin-swc`, supertest, Testing Library, MSW;
- tooling: Turborepo, ESLint + typescript-eslint, `eslint-plugin-boundaries`, Prettier.

## Architecture rules

- **Backend modules**: `identity`, `enrollment`, `booking`, `messaging`.
  - Each has the layers `domain/` (pure TypeScript, no Nest or Drizzle), `application/` (use cases and ports), `infrastructure/`, `controllers/`, plus a public `index.ts`.
  - Modules import each other only through `index.ts`, and there are no foreign keys across modules.
  - Queries go through ports; facts go through domain events emitted after commit.
- **Business rules** are enforced in both layers: the domain checks them, and database constraints are the final guard. "Now" always comes from the injected `Clock`.
- **API contract**: the OpenAPI spec is generated and committed. The Orval client is generated and git-ignored. Errors are Problem Details with stable `code`s.
- **Web**: feature folders mirror the backend modules. A feature imports only `shared/` and its own generated client module.
- **Tests**: test external behaviour at the highest seam. The primary seam is the HTTP API against the real test Postgres. Pure unit tests are only for combinatorial logic (slot alignment, DST week bounds).
